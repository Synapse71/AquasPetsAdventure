## 0. 上手

### 环境

```bash
~/.venvs/idle-art/bin/python -c "import PIL, numpy, scipy"   # 应当无输出
node --version                                                # 需要 18+（内置 WebSocket）
ffmpeg -version | head -1                                     # 处理动画要用
```

venv 里**没装 rembg**。只有 `tools/video2sprite.py` 需要它，而现在出动画走的是
`tools/video2frames.py`（floodfill 抠图，不需要模型）。除非遇到背景脏到 floodfill
处理不了的素材，否则不用装。

⚠️ venv 不要建在 `/tmp`——那个目录会被系统清空，本项目已经因此丢过一次 venv、
两份原型源码和四份校验脚本。同理，任何要跨会话留存的产物都直接写进项目目录。

### 改完原型必须跑的四件事

```bash
node tools/proto_smoke.mjs prototypes/<页面>.html     # 真执行脚本 + 逐视图渲染
node tools/page_console.mjs prototypes/<页面>.html    # 真实 Chrome 里有没有报错
node tools/checks/run-all.mjs                        # 69 条规则断言（从项目根跑）
node tools/rule_sync.mjs                             # 判定分档是否还和 engine.ts 一致
```

前两个**都要跑**：`proto_smoke` 的 DOM 桩里 `querySelector` 永远返回元素，
选择器打偏返回 null 这类错它看不见（详见 5.3.3）。改了 class 名尤其要跑第二个。

涉及点击 / hover 的改动再加一条，它派发真实鼠标事件：

```bash
node tools/ui_probe.mjs prototypes/<页面>.html '<选择器>' --setup "<摆状态的 DOM 操作>"
```

### 已知边界

- **老九段动画的 prompt 无法恢复**（liclick API 不返回原文、当时的会话记录已过保留期）。
  2026-09 之后新出的段都有 `prompt.json`。
- **数据缺口**（等策划）：93 件物品只有 13 件有 `description`；`petTemplates` 只有 1 个，
  多宠物 / 队伍相关的 UI 无法验证；`tags` 只有 2 个且「万人迷」无描述；两张地图 0 条隐藏路线。

  但原型里没有任何拖拽代码，这条规则从未被验证过。
- **睡眠链只有素材和文档，没实现**（产品阶段做），见第 4 节「待机调度与眨眼」。

## 2. 桌宠动画

**九段共用 960×902 画布，缩放系数通用；但各段的横向落点不同，那是设计。**

生成手法是**固定首尾帧**：首尾两帧都由锚点图钉死，模型只补中间。
首尾帧钉在哪，那一段就落在哪。实测躯干水平中心（取 55%~85% 画布高的带，避开道具）：

| 段 | 首帧 | 尾帧 | 含义 |
|---|---|---|---|
| `idle-magnifier` / `idle-digging` / `win-chest` / `lose-bag` | 480 | 480 | 站立自闭环 |
| `start-explore` | 480 | **358** | 站立 → 走向画面左侧 |
| `walk` | 400 | 400 | 接 start-explore 的落点，在左侧循环 |
| `sleep-start` | 480 | 489 | 站立 → 睡姿 |
| `sleep-loop` | 489 | 490 | 睡姿自闭环 |
| `sleep-end` | 490 | 480 | 睡姿 → 站立 |

⚠️ **`walk` 偏左 86px 不是缺陷。** 它是 `start-explore` 那段「走出去」的落点。
把它平移回中心，这条衔接链就断了。只有把某一段**单独拿出来原地播放**时才需要对位
（比如桌宠头顶进度条那个场景，行进中角色应当待在原位）——
用 `tools/pet_clip.py <段> --align`，产物带 `-aligned` 后缀，与原样版并存。

**真正的漂移是 `lose-bag`：首尾帧都在 480，中间帧漂到 553。**
中间帧是模型生成的，本地修不了，只能重出。用 `tools/anim_qa.py` 查这类问题。

垂直方向没问题：站立各段脚底在 ±7px 内。`sleep-*` 的躯干带测量对躺姿不适用。

| 动画 | 目录 | 帧数 | 时长 | 用途 |
|---|---|---|---|---|
| 待机 · 放大镜 | `idle-magnifier/` | 121 | 5.0s | 待机随机播放 |
| 待机 · 刨地 | `idle-digging/` | 121 | 5.0s | 待机随机播放 |
| 开始探索 | `start-explore/` | 121 | 5.0s | 待机 → 行走 的过渡 |
| 行走循环 | `walk/` | 115 | 4.8s | 探索中，可无缝循环 |
| 入睡 | `sleep-start/` | 121 | 5.0s | 长时间无交互后 |
| 睡眠循环 | `sleep-loop/` | 110 | 4.6s | 可无缝循环 |
| 醒来 | `sleep-end/` | 121 | 5.0s | 被点击 / 到时唤醒 |
| 结算 · 成功开箱 | `win-chest/` | 121 | 5.0s | 探索成功 |
| 结算 · 失败空袋 | `lose-bag/` | 121 | 5.0s | 探索失败 |
| 提示 · 注意到灯泡 | `bulb-hint/` | 122 | 5.1s | 有待处理事项时播一次 |
| 待机 · 站立眨眼 | `blink-plain/` | 122 | 5.1s | **默认待机态**（三段轮播之一，权重 3） |
| 待机 · 眨眼（呼吸） | `blink-breath/` | 122 | 5.1s | 同上，权重 3 |
| 待机 · 眨眼（歪头） | `blink-tilt/` | 122 | 5.1s | 同上，权重 1（整段只眨 1 次） |

每个目录下：`frames/frame_NNN.png`（960×902 透明 PNG）+ `anim.webp`（380px 预览）。

**帧率 24fps。** 循环段（`walk` / `sleep-loop`）的首尾帧是靠 PSNR 扫描找的天然回归点，
直接首尾相接即可，不要做交叉淡入——会重影。

**锚点链。** `anchor-front-standing.png` 是根锚点，所有动画的首帧都由它生成，
所以任意两段动画之间切换时角色形象一致。另有 `anchor-sleeping.png`、`anchor-walk-start.png`。

**桌宠本体宽度：站立时躯干占画布宽的 47%**（实测 451/960）。UI 布局要用到，见第 4 节铁律。

### 2.1 现在直接可用吗？——可用，但不该直接用原始 PNG

| 形态 | 体积 | 结论 |
|---|---|---|
| `frames/` 全部 PNG | **383 MB** | 只作母版，绝不进包 |
| `anim.webp` 全部（380px） | 18 MB | 能在浏览器直接播，但偏大且无法控制播放 |
| 单段动画 240px 动画 WebP | **785 KB**（121 帧 q60） | 推荐，九段合计约 **7 MB** |
| 单段动画 240px 雪碧图 WebP | 795 KB（2640×2486） | 与动画 WebP 体积相当，但能逐帧控制 |
| 同上 PNG 雪碧图 | 4.1 MB | 5 倍体积，不划算 |

**动画 WebP 的问题**：用 `<img>` 播的话，暂停、跳帧、"播完这段再切下一段"都做不到，
浏览器不给逐帧控制。而本作需要「入睡 → 睡眠循环 → 醒来」这种串联，以及
「醒来播到一半时菜单已经弹出」这种并行，都要能编程控制播放进度。

**所以推荐雪碧图 + 逐帧驱动**：体积和动画 WebP 持平，但换来完整控制权。
`tools/` 下还没有生成雪碧图的脚本，需要时说一声，配套的 JSON 应包含：
帧数、帧尺寸、列数、fps、是否循环、循环入点。

母版 PNG 保留在仓库里，任何时候可以按新的目标尺寸重新导出，不会有损失。

### 次要属性成长道具（8 件，2026-08-20 完成）

给宠物加口才 / 学识 / 勇气 / 狡黠的道具，每项一件神话（+2）一件传说（+1）。
探索过程、落选稿和定稿提示词都在 `loot/style-explore/secondary/`，
总览图 `_次要属性道具全八件.png`。

| 属性 | 神话 +2 | 传说 +1 |
|---|---|---|
| 勇气 | 雪滑勇闯田崖（棕玻璃啤酒瓶 + 蓝白滑雪剪影标签） | 拳击赛报名表（白纸 + 红拳套实物） |
| 口才 | 巧舌如簧（弹簧底座上的咧嘴玩具） | 《销售的自我修养》（橙色立着的平装书 + 白对话气泡） |
| 狡黠 | 灌铅骰子（黄金骰子 + 凹刻黑圆点） | 《三十六计》（墨绿平放的线装书 + 装订孔穿线） |
| 学识 | 布布糕点读机（焦糖布丁配色的儿童平板 + 点读笔） | 探险手稿（冷白散页 + 深棕皮绳 + 手绘地图） |

**这批做下来的三条经验：**

**一次做一组，让提示词互相点名。** 三本书那轮，每条提示词都写明另外两件长什么样、
必须避开，结果三件在装帧形制上主动分化（立着的平装 / 平放的线装 / 皮绳捆扎散页），
比各写各的效果好得多。同类物品扎堆时（这个项目已经有 6 个纸/书类物件）必须这么做。

**描述结构，不要描述损坏。** 灌铅骰子第一轮四张全把"缺口"画成了表面的凹坑，
因为"缺口""破损"这类词天然指向"洞"。改成纯几何描述——"一个顶角被整齐削掉，
形成三角形平整斜切面，三条边与相邻三个面相交"——并把"凹坑 / 圆洞 / 裂纹"写进负面，一轮就对。

**深描边风格下不必做预防性偏色。** 巧舌如簧是神话档（朱红底），我一开始怕红舌头糊进底色，
特意把嘴唇往洋红紫调推。实测证明**深描边一圈已经把色相接近的前景和背景完全隔开**。
早期"稀有度底色对比度不够"那条经验的前提是**无描边的浅色物件**（白石膏雕像、浅色纸张），
不能推广到带描边的物件上。真正需要避让的只有明度太接近的情况，色相接近不是问题。

### 致敬类物品的出图方式

传说档有一批向其他游戏致敬的物品（如 `card-stoat` 取自《邪恶冥刻》的白鼬卡）。做法：

1. **要原作截图当参考图**，不要凭文字描述硬编。第一版我只按"一只白鼬"来画，
   结果画成了写实可爱的小动物——**辨识度不在物种上，在那张呆滞不爽的粗线条脸上**，
   丢了这个特征就完全认不出来了。
2. 参考图的用途必须在提示词里**限定死**："照搬构图和角色神态，但用我们这套扁平粗描边风格重画"，
   同时把原作的质感特征写进负面（白鼬那次写的是「粗糙划痕笔触、噪点质感、像素颗粒、手绘铅笔感」）。
   不限定的话，参考图会把风格整个带偏，和其余 80 多件对不上。
3. 卡面上的文字数字按「只解禁需要的那几个字符」处理，白鼬那次只放行了 `STOAT` `1` `3`。
4. **原作是彩色、我们要改材质时，识别特征会跟着一起丢。** 绚丽之门雕像要求做成白石膏，
   而原作的红帘、绿眼珠、红玫瑰三个彩色识别点在纯白里全部消失，只能靠浮雕起伏表达——
   提示词里要把每个特征都写成"雕出来的"，并在负面里点名原来的颜色（红色帘子 / 绿色眼珠 / 红色玫瑰），
   否则模型会偷偷把颜色加回来。
5. **门、窗、环这类"能穿过去"的物件，中间的洞必须保持透空**，那是它剪影的核心。
   绚丽之门有一版把门洞画成了实心灰板，立刻读成镜子或神龛，不像门了。
6. **别凭印象描述参考图，先把像素读出来。** 五彩碎片那轮我把形状写成"竖长多面体"（实际宽高相等）、
   色序写成"左红右紫"（实际左蓝右紫），两处都错。参考图的外接框尺寸、逐行轮廓宽度、
   每行的颜色序列全都可以直接量，量完再写提示词。
7. **文字描述和参考图会抢方向盘。** 一边挂低分辨率参考图、一边在文字里详细描述造型，
   两边不一致时模型只能二选一——选文字就跑形，选参考图就是糊的马赛克。
   解法是拆成两步：第一步**只做忠实高清化、完全不提风格**；
   第二步拿高清图当参考**只改画法、完全不描述造型**（提示词里只说"严格保持参考图的轮廓"）。
   五彩碎片用这个办法把高宽比从 1.73 拉回到 1.02。
8. **纯改材质的返工，变体描述里只许出现颜色和明暗词汇。** 绚丽之门改废金属时，
   我在变体里写了"磨损更重""对比更强"这类整体性形容，结果两格把柱顶的火焰装饰改成了圆盘状物件——
   **差异描述会泄漏成造型改动**。
9. 定稿提示词存 `loot/style-explore/prompt-card-stoat.json`、`prompt-florid-postern-statue.json`、
   `prompt-icarus-mech-model.json`，新物品照着改。

### 铁律：菜单总宽不得超过桌宠本体宽度

本体宽 = 画布宽 × 47%。菜单宽度必须由它算出，不能写死常数：

```css
--body:    calc(var(--canvas) * .47);
--gap:     4px;
--bubsize: calc((var(--body) - 4 * var(--gap)) / 5);
```

**五个按钮保持一行**，靠缩小气泡直径 + 收紧间距满足铁律，不换成两行（两行难看）。
当前画布 300px → 本体 141px → 五颗 25px 气泡加四个 4px 间距，正好 141px。
**图标占直径的 92%**，按外接圆归一化，只留一圈细边。
桌宠被拖到屏幕边缘时，菜单整体内推，不允许被裁。

**加按钮的代价可以用放大桌宠抵消**：整套参数化，画布放大按钮跟着放大。
要让五颗按钮回到 32px，画布需渲染到 `374px`（`5×32 + 4×4 = 176 = 374 × .47`）。
所以真正要定的是「桌宠在屏幕上多大」，不是「按钮多大」。

**五个是这个宽度下的上限。** 第六颗会掉到 20.6px、图标不足 19px，低于可用下限；
之后要加功能应往二级面板里塞，不要继续加气泡。

**按外接圆归一化，不是按外接框。** 圆形按钮里「看起来多满」由离重心的最远半径决定；
按外接框归一化会让细长形状（三角旗）显小、方形显大。做法是把每个图标缩放到
最远半径 = R×k、画布边长恒为 2R，于是四个图标共用同一个外接圆——
**这样 CSS 里的百分比才是真的百分比**，100% 正好内切圆边，当前用 92% 留一圈均匀细边。
k 是视觉体量补偿，密实形状收一点（齿轮 0.94），免得比别人重。

两个曾经踩过的坑：
- **内边距不要烘进图片。** 早期画布自带 20% 内边距，CSS 写 88% 实际只占直径 70%，
  看起来图标偏小，而且后面每个人调 CSS 都在跟一个看不见的系数较劲。
- **按重心居中时画布必须够大**，否则会把图形裁掉一角。曾经三角旗的旗杆底部被切掉 40px，
  外接框只剩画布的 91%，百分比又被打了一次折。现在画布由外接圆半径反推，不可能裁到。

另有一个坑：模型会把每个图标画在**各自的浅灰面板上、面板间留白缝**。
抠图必须先按面板边界裁进去再抠，否则四角 flood fill 只吃掉白缝，把灰面板当成物体。

### 头顶进度条

派出探索后桌宠切 `walk/`，头顶浮出进度条。**它是状态读数，不是交互**——
菜单展开时照常显示，也不响应点击。

| 参数 | 值 |
|---|---|
| 宽度 | `= 本体宽`（当前 141px），与脚下菜单同宽，遵守同一条铁律 |
| 头顶净空 | `8px`，按**角色头顶**算 |
| 内容 | 目的地 + 剩余时间 `mm:ss`（等宽数字）+ 填充条 |
| 进出场 | `180ms` + `4px` 上浮；走满后停 `700ms` 再淡出 |
| 底色 | 与气泡同款半透明 + `blur(6px)` |

⚠️ **净空要按角色头顶算，不是画布顶。** 960×902 画布上方有留白，
`walk` 抬头帧的头顶在 **3.7% 画布高**处（九段里最高），按它反推才不会被顶到。
用 `idle` 的 4.9% 会在行进中重叠。

⚠️ **`top` 定位的是条的底边**，配合 `translateY(-100%)`。
先前把条的高度写进 `top` 的公式里，`--hud-h` 写 29px 而实际渲染 31px，
净空直接从 8px 缩到 2px。定位量不要依赖元素自身高度。

**进度按已走过的时间算，不按剩余。** 剩余取整后条会在最后一秒突然跳满。

### 待机调度与眨眼

桌宠平时在**五段待机动作**之间随机切换，长时间没人理会就去睡觉。

| | |
|---|---|
| 五段待机 | `idle-magnifier` `idle-digging` `blink-plain` `blink-breath` `blink-tilt`，**地位平等** |
| 平时 | **固定帧**（站立静态图 `still-standing-240.png`），不循环任何动画 |
| 间隔 | 回固定帧后停 **6s** 再播下一段。周期 `5.1 + 6 = 11.1s`，约 **46%** 时间在动 |
| 不重复上一段 | 纯随机会连着抽到同一段，看起来像没换 |
| 权重 | `2:2:5:5:2`——眨眼三段合计 **71%**，放大镜/刨地是偶尔露一次的性格戏；`blink-tilt` 压到同档（整段只眨 1 次）。实测 14.5/14.5/28.3/28.3/14.4% |
| 眨眼频率 | 约 **11 次/分钟**（真人 15~20）。各段实测眨眼数：`idle-magnifier` 0、`idle-digging` 2、`blink-plain` 3、`blink-breath` 3、`blink-tilt` 1 |
| 进入睡眠 | **3 分钟无交互** → `sleep-start`(5.0s 一次) → `sleep-loop`(4.6s 循环) |
| 退出睡眠 | 玩家**点击桌宠** → `sleep-end`(5.0s 一次) → 回五段待机 |
| 优先级 | 行进 > 灯泡提示 > 睡眠 > 待机 |

睡眠链端点实测咬合：`sleep-start` 480→489、`sleep-loop` 489→490、`sleep-end` 490→480，
可以直接串起来，不需要过渡。

⚠️ **五段的脚底必须落在同一条基线（y=852）上**，否则随机切换时角色会跳。
三段眨眼和 `bulb-hint` 原先在 846，因为 `video2frames.py` **先按含地面阴影的最低点
定了裁切、之后才去阴影**，基准被阴影污染。已修：脚底改用「抠图 + 去阴影后」的首帧来量。
现存各段实测脚底 852~855、角色高 807~811（±0.5%，模型生成的正常波动）。

`prototypes/pet-menu.html` **只演示了固定帧 + 五段随机播放**，睡眠链留到产品阶段。

⚠️ **间隔是「回到固定帧之后再停多久」，不是固定周期。** 按固定周期触发的话，
换一段时长不同的动画，静止时间就跟着变了。

⚠️ **所有动画帧只由 `data-pose` 一个属性决定谁可见。** 早先用
`.stage.acting` / `.stage.hinting` / `.stage[data-blink]` 几组 class 分别控制，
它们特异性相同（都是 4 个选择器）、全靠书写顺序才不打架，段数一多必然出错。
收敛成一组规则后，加段只要加一行。

### 灯泡提示

有待处理事项（任务可领、升级有属性点没分、探险到站）时，角色右上方浮出一个灯泡，
并播一次 `bulb-hint`「注意到灯泡」的动作，之后回待机，灯泡挂着直到玩家处理掉。

⚠️ **灯泡是独立的 UI 组件，不在动画帧里。** 它要能点（点击跳到待处理的界面），
烘进帧就只能做坐标热区、桌宠一缩放就错位；而且模型保不住它静止——
`bulb-point` 原片里灯泡在 f54 缩到了约 75%。

生成时灯泡**要**画在锚点图里（模型需要视觉参照，否则角色对着空气反应、视线会飘），
生成完用首帧 mask 把它抹掉。位置换算：

| | 值 |
|---|---|
| 帧内矩形 | `x 762~890 / y 46~236`（960×902 画布） |
| CSS | `left:79.375%; top:calc(--canvas * .93958 * .051); width:13.333%; aspect-ratio:128/190` |
| 素材 | `assets/ui-prototype/icons/bulb.png` |

`prototypes/pet-menu.html` 底部自检会核对左缘 / 顶边 / 宽度三个数。

**灯泡默认不做任何自发动效**（只有 hover 放大）——「灯泡不能动」是硬要求，
要加呼吸提示得单独确认。

**灯泡不区分提示类型**（2026-09-09 定）。到达地点、任务可领、升级有属性点未分配……
来源不同但都用同一个灯泡，点击直接跳到待处理的那个面板。
换图标或加角标区分类型的方案**已否决**：玩家得先学会解读图标才知道是什么事，
多一层认知负担，而点进去本来就看得到。

同时有多件待处理时，跳**优先级最高**的那一件（顺序待产品阶段定），
不要做成需要玩家在灯泡上选择的菜单——那就退回到"先解读再操作"了。

### 交互规则

- **睡眠态点击：醒来动画与菜单弹出同时开始。** 不等醒来播完——`sleep-end/` 有 5.0s，
  等它播完再弹菜单会让人以为点击没生效。
- **收回顺序与弹出相反。** 同向会让人觉得菜单没关干净。
- **收回比弹出快**，且只有弹出带回弹。回弹用在退场上会显得黏。
- **菜单展开期间暂停待机动作的随机切换**，避免菜单还在弹、桌宠突然换了个动作。

### 库存面板

左右分栏，**探险背包与库存主从同屏**，原型 <https://claude.ai/code/artifact/89ae8fbd-acf8-47df-8ecf-176825123c53>。
面板主体永远是库存；探险期间顶部那条换成「背包（探险中）」，未探险时显示「当前没有队伍在外探险」。
两者同屏可见不需要切换——探险中要判断「这件该不该丢」，得能同时看到库存里已经有什么。

**四条容量，口径各不相同，最容易记混：**

| | 上限 | 备注 |
|---|---|---|
| 探险背包 · 负重 | `(5 + 体能 × 1.2) × 伤势倍率`，队伍相加 | 体能 3 → 8.6 |
| 探险背包 · 格数 | `8 + 技巧 × 1`，队伍相加 | **不乘伤势倍率**。技巧 3 → 11 格 |
| 库存 · 格数 | `warehouseSlots`，初始 40，扩建每次 +10 | |
| 库存 · 负重 | **无限制** | 仓库只卡格子，不卡重量 |

**格子占用 = `Σ ceil(数量 ÷ stackSize)`，不是「一种一格」。**
麻绳 `stackSize 12`，带 17 根占 2 格。空格子要常驻显示，玩家才知道还能再捡多少。

**两条约束各有各的指示器，不合并成一个「满了」。** 负重是连续量、格数是离散量，可以单独触顶：
捡一口 4 点的铸铁锅先压负重，捡一堆小杂货先用光格子。合成一个进度条，
玩家就不知道该丢重的还是该丢杂的。超载提示必须说明是哪一条爆了、还差多少。

**展开明细是绝对定位的浮层**，盖在网格上方而不是把面板撑高（见 5.2 铁律）。
展开唯一的用途是超载时决定丢什么，所以每行列出 名称 / 重量 / 价值 / 丢弃。

**结算区已砍掉**：撤离后不再有常驻的第三个容器，直接弹一次结算窗、点收下全部入库。

### 状态面板

单栏罗列布局，原型 <https://claude.ai/code/artifact/c53dc91c-1cb5-4c04-b76e-a0722ee4e710>。

| | 内容 |
|---|---|
| 主属性 | 体能 / 感知 / 技巧。**没有上限，所以用数字不用进度条**——进度条隐含有上限，会误导玩家照着一个假满值判断练到几成 |
| 次要属性 | 口才 / 学识 / 勇气 / 狡黠。**不写上限**——玩家关心的是「够不够进这扇门」，写 `2 / 20` 会让人以为要练满 |
| 伤势 | 正常 ×1、受伤 ×0.75、失能 ×0。恢复 30 分 / 4 时，**只在基地流逝** |
| 特质 | 最多 2 个（`growthTagSlots`）。目前全表只有「幸运儿」 |

**这块面板最需要传达的规则**：受伤只削主属性和负重，**不削次要属性，也不削格子上限**。

派生值两张卡并排，负重卡受伤变红、格子卡不变——一红一不红比任何文字说明都清楚。

**加点是暂存 + 确认两步**：点 `+` 只进暂存，可以连点几下先看派生值怎么变，再确认或撤销。
确认按钮放在主属性下方一条**常驻固定高度**的行里，空闲时 `visibility:hidden`（不是 `display:none`）。
洗点 `resetPetStats()` 是全量重置，**系统已实现存档共用递增收费**：0 / 500 / 2000 / 10000 / 30000，之后恒为 30000；只有成功提交才扣费计次。
原型里固定 500 货币仍只是旧占位，不可照搬。两处确认都做在面板内，不用浏览器原生 `confirm()`：
桌宠是悬浮层，原生弹窗的位置和层级不可控。

### 任务面板

做在探险面板里，顶部标签【探险 | 任务】。数据取自 `catalog.tasks`（5 条，两条任务线）。

**归属：行动 · 三角旗**，不新增气泡。五颗气泡已经占满桌宠本体宽度（141px），
第六颗会掉到 20.6px、图标不足 19px，低于可用下限（见本节铁律）。

**分流方式：顶部标签页。** 点开行动旗直接落在探险第一步（选宠物），
顶部是【探险 | 任务】两个标签；**一旦往下走进入探险流程，标签隐藏、换回步骤指示器**。
这样探险是零额外点击，任务一键可达。

理由：探险是**高频日常循环**，任务是**低频主线推进**（解锁地图、加新宠物、扩仓库全靠它）。
高频的那条路不能被低频的挡住——这也是没选「入口页二选一」的原因，
那个方案结构更清晰，但每次探险都要多付一次点击。

任务标签上挂**可提交数量的角标**，否则低频功能没人会主动去翻。
（气泡按钮本身要不要也挂角标还没定。）

标签出现时面板标题写「**行动**」，其余阶段写「探险」——
标题写死「探险」会和标签里的「探险」重复成「探险　探险 | 任务」。

**任务自动接取，没有日常任务**；任务之间靠 `prerequisiteTaskIds` 串成**任务线**，
完成一条线上的任务会自动接上这条线的下一个。所以列表里显示的永远是
**每条线的当前那一个**——已完成的不再出现，前置没完成的也看不到。
不要设计「接受任务」按钮，引擎里没有这个动作。

**引擎的任务能力**（`taskIsAvailable` / `taskCanComplete` / `completeTask`）：

- **没有「接取」这个动作**，状态只有 `completedTaskIds`。所以任务只有三态：
  前置未完成（不可见）、可见但条件不够、可提交。UI 不要设计「接任务」按钮。
- 条件三类：交物品、交货币、**通关地图**——注意 `mapIsCleared` 要求从**固定终点**撤离，
  中途撤离点撤离不算通关。
- 奖励五类：货币、解锁地图、获得新宠物、仓库扩容、物品。
- ⚠️ `taskRewardFitsWarehouse()`：**奖励物品直接入库，仓库放不下就不能提交**。
  它计算时会算上「提交物品腾出的格子」和「本任务的扩容奖励」，
  所以 UI 上的「放不下」提示要按最终状态算，不能只看当前剩余格数。
- goal 有**两种**类型：`clear-map`（通关地图）和 `milestone`（一次性玩家行为，
  定义在 `src/domain/milestones.ts`，目前 5 条都是「打开过某个面板」）。
  别看到 goals 就当成通关条件——`tasks-game-start` 用的就是 milestone。
  客户端要在面板打开时调 `recordMilestone()` 上报，否则这条新手任务永远完不成。

需求项的物品进度**直接读仓库真实数据**（和背包、撤离是同一份），不另设一套计数。
回归脚本 `task-verify.mjs`（scratchpad）验：任务数据与 catalog 逐字一致、
任务线自动接续、每条线同时只暴露一个、四类条件各自都能卡住提交、
提交后正确扣料发奖、仓库放不下时挡住提交、角标数与可提交数一致。

### 起点是特例，别当成普通节点

出发后行进抵达的第一个位置是地图起点，引擎在 `engine.ts` 里给它开了单独分支
（`node.id === map.startNodeId && completedNodeCount === 0`）：

- `arrivalLoot = {}`，**没有战利品** —— 不要进宝箱页，玩家会对着一个空箱子发愣
- `currentEventId = undefined`，**不触发事件**
- `phase = "awaiting-route"`，直接进选路线
- `continue` 跳过后面的计数，**不计入 `completedNodeCount`** —— 所以也不给节点经验

原型里一开始是无条件 `S.stage="arrive"`，起点就变成了一个空宝箱页，
还白送了一次节点计数和 10 点经验。三条都得对齐。

注意这个特例**只在首次抵达时成立**（`completedNodeCount === 0`）：
路线绕回起点时按普通节点处理。

另外非起点节点引擎要求**必须配 `loot`**，没配会直接
`throw new GameRuleError`。UI 侧不该跟着崩，但也别显示空宝箱——跳过这一步即可。

### 重量只在背包那条链路上有意义

`GameState.warehouseSlots` 的注释写着「**仓库只限制格子数，不限制重量**」。
所以重量这个数字只在**探险背包**里有用（负重上限 → 超载惩罚 → 事件风险），
东西一旦入库，重量就是个没人看的死数字。

战报里原本每件物品右侧显示的是重量，那是通用的 `itemRow()` 顺带来的。
已改成**售卖价值**，并在下方给出「入库战利品价值 / 就地售卖所得 / **总计收益**」三行，
总计加粗、上下描边。玩家判断「这趟值不值」靠的是钱，不是斤两。

⚠️ 改的是 `itemRow()` 的一个可选参数（`metric="weight"|"value"`），
**不要把这个函数全局改成显示价值**——事件结果页也在用它，
那里的奖励是直接进背包的，玩家需要知道会不会因此超载，重量在那里是有用的。

### 探险途中要能丢东西，否则超载是个死局

引擎 `discardCargo` 开放在 **awaiting-event / awaiting-route / extraction** 三个阶段，
注释写明用途：「玩家可以**先丢弃重物降低本节点事件风险**，再作选择」。
原型里对应 **抵达节点 / 遭遇事件 / 选择路线** 三页，各自在操作行放一个「整理背包」入口。

这不是可有可无的便利功能——超载惩罚会直接加进事件风险（+1/+2/+4），
**没有丢弃入口的话，玩家贪心多拿之后只能一路扛到撤离，那个惩罚就成了单向的惩罚而不是取舍**。

**入口做成顶栏常驻的背包按钮**（`ui-prototype/icons/bag.png` + `12.6 / 7.4`），
图标就用气泡菜单那枚背包按钮的图——同一个东西在桌宠上和面板里应该长一样。
⚠️ 那批图标是**按外接圆归一化**的（给圆形气泡用），四周留着 20% 空白，
放进方形小按钮会明显显小，要先裁到内容外接框再缩放。
出发之后的每一页都在——行进、抵达、事件、选路线。
一开始我把它做成操作行里的「整理背包」按钮，只在能丢的那几页出现，这是错的：
**背包是随时想看就该能看的东西，不是某几页才解锁的功能**。

行进途中引擎不放行 `discardCargo`（`traveling` 会抛错），
所以那一页背包能打开、能看负重和风险，但丢弃按钮不出现，写明「抵达后才能整理」。
按钮点击也要在动作层再拦一道，不能只靠不渲染按钮。

**超载时按钮标红并直接写出风险加成**（`12.6 / 7.4 +4`）：
这是玩家唯一能主动压低事件风险的手段，不标出来等于没有。

浮层里放负重条、事件风险、格子占用，点一件东西才出现「丢 1 件 / 丢 N 件」，
丢空了自动收起。撤离页不放这个入口——那里整页就是背包，卖掉也比丢掉划算。

### 撤离点是配出来的，不是默认的

引擎 `requestExtraction()` 的判定（`engine.ts:1583`）：

```ts
if (!node || expedition.currentNodeId === map.startNodeId
    || (!node.terminal && !node.extractable)) { /* 不能撤离 */ }
```

也就是 **能撤离 = 终点 或 显式标了 `extractable`，且当前不在起点**。
注意起点那条判断在最前面，**起点即使被标上 `extractable` 也撤不了**。

`map-1` / `map-2` 当前都**只有终点可撤离**，营地、树洞这些中途节点都不是撤离点。
原型里一度对所有非终点节点都画出「就地撤离」，文案还写着"任何非终点节点都可以撤离"——
那是早期规则的残留。选路线页要按 `canExtractHere()` 决定画不画这个按钮。

顺带两条连带修正：
- 地图上营地的节点形态本来标成「可撤离节点」（虚线圆），要改回普通节点，
  否则玩家在地图上看到撤离点、走过去却撤不了。
- **图例只列这张图上真出现过的形态**。map-1 没有可撤离的中途节点，
  图例里却画着那个符号，玩家会在图上找一个不存在的东西。

### 撤离整理

和出发前的 cargo、抵达节点的战利品共用同一套双栏格子（`.loadout / .lo-col / .cellslot`），
只是左右换成 **左探险背包 / 右仓库库存**：左键移单个、右键移整格，双向。
**放进仓库的入库，留在背包里的一律就地售卖**——比原来"每件三选一（入库/售卖/丢弃）"
少了一层决策，而且和玩家已经熟悉的搬运手势一致。

⚠️ **但"什么都不做"不能导向不可逆的结果。** 入库是可逆的（东西还在，以后随时能卖），
售卖是不可逆的；隐式售卖等于把最危险的那个结果设成了默认值，
玩家没看懂界面直接点确认，古旧硬币这种传说物品就变成金币了。
所以点「确认撤离」时**必须先弹一次售卖确认**，列出每件物品、单项金额和合计，
两个按钮是「返回整理」和「确认撤离」。
背包已经清空时不弹——没东西可卖还打断一次是多余的。

⚠️ **右栏是完整仓库，但只有本次新入库的格子能取回。** 仓库里出发前就存着的同名物品
（比如老库存 8 条麻绳、这次又带回 2 条）绝不能被"取回来卖掉"。
做法是进入撤离阶段时 `enterExtract()` 给仓库拍一张快照 `S.whBase`，
`freshQty(id) = 现有数量 − 快照数量` 就是可取回的上限；
能取回的格子加一圈强调色边框，其余置为不可点。
结算时"入库清单"也用同一个 diff 算，`S.cargo` 里剩下的才是售卖额——
不要用「按 dest 标记分类」那种写法，物品在两栏之间来回搬时标记会漂。

回归脚本 `extract-verify.mjs`（在 scratchpad）验的就是这几条：
40 次来回搬运总量守恒、连点 20 次取回也拿不走老库存、全入库再全取回能精确还原、
结算时"入库 + 售卖 = 带回"一件不差、仓库满 40 格后开不出新格、
以及确认层的三条路径（该弹时弹、取消能还原、背包空时不弹）。

### 随机事件（探险第 9 步）

**做在探险面板里**（`prototypes/event-panel.html` 曾短暂存在，已删除——
UE 要连贯，事件不该是一个独立页面）。事件阶段的三个子步骤共用同一块固定高度的主区：
**选择应对方式 → 判定 → 结果**，靠 `S.evtStep` 切换，外层面板尺寸全程不变。
14 个事件与全部数值都直接读 `catalog.bundled.json`，调试栏可逐个切换。

集成在探险面板里的额外好处：**风险里的超载惩罚用的是当前真实背包重量**，
所以「抵达节点时贪心多拿」→「事件风险变高」这条因果在面板内闭环了——
背包塞到 135% 时，难度 4 的选项风险会从 2 涨到 6，刻度条整条变红、直接标「本次判定无法成功」。

**引擎有三种判定类型，UI 表现必须分开**（`EventChoiceResolution`）：

| 类型 | 引擎行为 | 面板怎么表现 |
|---|---|---|
| `primary` | 掷 d6，`结果值 = 骰点 − 风险`，四档 | 刻度条 + 骰子动画 |
| `secondary` | **不掷骰**，够阈值成功、够高阈值大成功 | 三段轨道 + 指针，**不要出现骰子** |
| `leave` | 直接离开，无判定无收获 | 跳过判定，直接进结果 |

**`secondary` 最容易做错的一点：它没有失败分支。** 队伍属性低于 `successThreshold` 时
`isChoiceAvailable()` 直接判定该选项不可选（灰掉并说明差多少），
所以**只要玩家点得动，就一定不会失败**，区别只在够不够 `extraSuccessThreshold`。
面板上要把「必定成功」明写出来，否则玩家会以为这也是在赌。
另外它取的是**队伍最高值**（`teamSecondaryStat` 用 `Math.max`），
不像主属性那样有「主力 + 每名助手 +1」的加成。

**掷骰页顶栏只写风险值本身**，难度、主属性、超载、伤势四项明细收进右侧一枚小问号，
悬停展开。风险值是玩家唯一要记住的数，构成明细是"想深究时才看"的内容，
平铺在顶栏会把一行字撑成一串算式。
问号贴着容器右边缘，tooltip 要**向左展开**——`bindTips` 默认左对齐会让浮层大半飘到面板外，
给触发元素加 `data-tip-align="right"` 即可，不要去改通用定位逻辑（物品格子还在用）。

**掷骰页用一条连续色带表示每个点数的结果**，四段颜色固定：
`大失败 --rb-bad 红 / 失败 --rb-fail 黄 / 成功 --rb-ok 绿 / 大成功 --rb-great 紫`
（深色主题整体提亮一档，见 `:root` 里的 `--rb-*`）。
命中的那一格加白色内描边 + 顶部白三角。
**不要再挂图例和成功率文字**——颜色本身已经说明结果，绿段有几格玩家自己会数。
这四个色同时用在结算 chip 和结果页 chip 上，全局一套，
不能出现「色带里大成功是紫的、结果 chip 却是金的」这种对不上的情况。

**选项列表只写「用哪项属性判定」，风险 / 难度 / 成功率一律不上卡片。**
一屏三个选项、每个都挂三四个数字时，玩家读到的是一堆参数而不是一次抉择。
这些数字挪到判定页——那里只有一个选项，刻度条把 1..6 逐点标出会落到哪一档，
玩家在掷之前照样知道自己要 roll 几点。
属性标签不管够不够都只写图标 + 属性名，**不要写阈值、不要标红**——
不达标的选项整张卡片置灰就够了，再挂一枚红标签是重复喊话。
每张卡片固定两行，可选和不可选的排版完全一致。

具体数字改由**悬停提示**给出，内容按情报档位分级，
规则直接照搬引擎 `getRiskPreview()`，不要自己另立一套：

**判定分档的阈值以 `engine.ts` 为唯一事实来源，不要在原型里另记一份。**
同一组数字会散落在四处——`resolveEvent()` 的判定、`primaryOutcomeProbabilities()` 的概率枚举、
掷骰页的「成功需要 ≥N 点」、以及页面文案，漏改一处就会出现
「色带显示会成功、掷完却判失败」这种前后对不上的表现。
引擎改过规则后跑 `node tools/rule_sync.mjs`，它直接从引擎源码抠阈值再逐文件比对。
（2026-08-28 已从 `≥7 大成功 / ≥2 成功` 改为 `≥6 / ≥3`。）

| | 主属性选项 | 次要属性选项 | 直接离开 |
|---|---|---|---|
| 情报缺失 | 「风险未知 / 感知属性不足，无法判断这个选择的危险程度」 | 「学识不足」（只在不达标时） | 「安全离开」 |
| 部分情报 | 档位 + 受伤程度白话（不会 / 有小概率 / 有大概率 / 有极大概率受伤） | 「需要学识达到 3」 | 同上 |
| 完整情报 | 档位 + 四档概率**各占一行**（两列网格，数字右对齐） | 成功线与大成功线，两行完全同样式 | 同上 |

**档位不要只甩四个形容词给玩家。**「冒险」「危险」这类词本身没有信息量，
配一句后果——大失败就是有人受伤，所以直接写成「有小概率受伤 / 有大概率受伤 / 有极大概率受伤」。
情报缺失档说的是「**感知属性**不足」而不是笼统的「情报不足」，
因为档位就是队伍感知总和算出来的，玩家要能顺着这句话知道该去练什么。

**并排的数值一律用两列网格，不要用「· 」串成一行。**
风险明细和四档概率都是 `标签 + 数值` 的结构，塞进一行读起来是一串符号；
拆成每项一行、数值右对齐 + `tabular-nums`，扫一眼就能比大小。
两处共用同一套 `.rk` 样式。

**tooltip 的每一行要自己声明是标题还是正文。** 成功条件和大成功条件是**并列**关系，
两行必须**完全同样式**：同为标题、同一个颜色。
一行标题一行正文会读成从属关系；给两行分别上绿 / 金也一样——
只要有差异，读者就会去找差异的含义。并列就是并列，别自作聪明加层次。

**tooltip 标题一律不用纯黑 `--ink`。** 风险档位那几个标题分别是
`--ok` / `--ink-2` / `--accent` / `--warn`，中间那档就是 `--ink-2`；
无色可上的标题（比如成功条件）跟着用 `--ink-2`，不要留默认的纯黑——
一堆柔和标题里蹦出一行纯黑会很跳。改色时用截图取色核对实际渲染值，别只看代码。

档位由 `mapInformationTier()` 按**队伍感知总和**算，阈值默认 `{partial:2, full:4}`。
风险档位看的是**大失败概率**（不是失败概率）：`0 稳妥 / ≤0.3 冒险 / <0.6 危险 / 其余极其危险`。
概率用枚举法算，优势骰要枚举 36 种组合取高，不能拿单骰概率平方去凑。

⚠️ **不可选的选项不能用 `disabled` 属性**——Chrome 下 disabled 元素不触发 `mouseenter`，
而这些选项恰恰最需要提示。改用 `aria-disabled="true"`，点击拦截在事件处理里自己判断。

**事件奖励是引擎直接塞进 `expedition.cargo` 的**（`resolveEvent` 里一行 `addInventory`），
不像节点战利品那样要玩家点击拾取，所以结果页必须写明「已直接放入背包，无需拾取」。
⚠️ 引擎在这里**没有做背包格上限检查**，塞满了会怎样目前无定义，需要系统 agent 补。

**不是每个事件都能撤离。** 14 个事件里有 4 个（拦路的蟊贼、正在坍塌的旧通道、
围拢的野犬群、暗藏机关的路障）**没有 `leave` 选项**，描述里都写了退路已断。
这类事件要在事件卡上打「无法撤离」标记——玩家扫选项列表时未必会注意到少了一项。

**惨败会真的减员**：`injureRandomPet` 让随机一名成员伤势加重，全员失能则整场探险失败
（`finishDefeat`）。结果页除了 summary 还要单独给一条伤势提示条，
并说明后续判定的伤势惩罚会增加——这是玩家决定继续还是撤离的依据。

## 5. UI 实现踩坑（做界面的人必读）

### 5.1 用 `<button>` 当图标按钮，先写 `padding:0`

浏览器给 `<button>` 的默认内边距是 `1px 6px`。配上全局 `box-sizing: border-box`，
一个 `width:31.5px` 的圆形按钮，内容区只剩 `31.5 − 1×2(边框) − 6×2(内边距) = 17.5px`。
子元素写 `width:92%` 是**相对内容区**算的，于是图标只有 16px，占直径 51%。

同样写 `92%`，`<div>` 做的圆圈（无默认内边距）得到 35/40 = 87%，`<button>` 得到 51%。
两处摆在一起就是"比例不一致"，但 CSS 里两行代码一模一样，光看代码看不出来。

```css
.bub {
  width: var(--bubsize); height: var(--bubsize);
  padding: 0; margin: 0; font: inherit; line-height: 0;  /* 缺这行，图标缩水 40% */
  display: grid; place-items: center;
}
```

### 5.2 铁律：任何交互都不得改变面板的宽高

面板一旦因为点击而长高或变宽，桌宠悬浮层就会跳动，观感立刻廉价。这条比"多一行更好看"重要。

**做法是把会出现/消失的元素改成常驻的固定高度槽位，只换内容不换高度：**

- 加点的「确认 / 撤销」不新起一行，塞进「主属性」那一行右侧——那行本来就存在。
  待分配 / 确认分配 / 确认重置三种状态共用同一个 `height:40px` 的槽位。
- 伤势提示条常驻 `height:38px`：正常时显示「状态良好，可以出发」，
  受伤时才换成恢复倒计时和治疗按钮。不要用 `${cond ? row : ""}` 这种写法。
- 库存面板同理：详情栏的描述固定两行高度，史诗及以下留空占位；`.body` 定高、左栏内部滚动。

**容易漏掉的破坏源**（都实际发生过）：

| 破坏源 | 现象 |
|---|---|
| 条件渲染整行 | 加点确认条一出现，面板长高 |
| 状态切换导致的行增减 | 切到「受伤」时多出恢复提示条 |
| 文案长度变化导致折行 | `560（280 × 2）` 在窄栏折成两行 → 给数值加 `white-space:nowrap` |
| 描述有无 | 传说物品有描述、史诗没有 → 固定两行高度 + `-webkit-line-clamp:2` |
| 数字位数变化 | 999 → 1000 挤宽列 → `font-variant-numeric: tabular-nums` |

**自检方式**：在原型里加一段 `getBoundingClientRect()` 读数，每次渲染后和首帧尺寸比对，
不一致就显红。状态面板原型下方就有这个读数，点任何东西它都不该变。

### 5.3 原型发布前必须跑运行时冒烟，语法检查不算数

`new Function(script)` 只解析不执行——TDZ（`const` 声明顺序错误）、未定义变量、
空引用这类**运行时错误全部抓不到**。探险面板曾因为把 `MAP_SLIDES` 插在它引用的
`MAP_DESC` 之前，语法检查通过、发布出去整页白屏，被用户抓到。

发布前跑 `node tools/proto_smoke.mjs prototypes/<页面>.html`：
真执行整段脚本（最小 DOM 桩）+ 逐阶段渲染每个视图函数。四份原型都要过。

### 5.3.1 校验脚本必须放进仓库，不能留在临时目录

规则校验有两层，都在 `tools/` 下：

| 工具 | 干什么 |
| --- | --- |

DOM 桩：`loadProto(file, expose)` 把原型的整段脚本跑起来，再把指定的内部函数
暴露出来做断言。新增面板时照着抄一份即可，`run-all.mjs` 按文件名自动发现。

**这些脚本一度写在会话 scratchpad 里，被系统当临时文件清掉了四份**，
29 条断言（起点特例、任务线、撤离守恒、情报分档）一起消失，重建花了不少时间。
和 venv 那次是同一个教训：**`/tmp` 下的任何东西都不算存在过**。
校验是回归资产，必须跟着仓库走。

### 5.3.2 交互不生效时，先验「事件能不能到」，不是「样式对不对」

灯泡的 hover 连着两轮没修好，两轮都是验证方式选错了：

| 轮次 | 我做的 | 为什么没用 |
|---|---|---|
| 1 | 发现 `.bulb:hover`（1 类+1 伪类）被 `.stage.hint .bulb`（3 类）的 `transform:none` 盖住，改成 `.stage.hint .bulb:hover`。用「加一个同特异性的类」量到 transform 1→1.08 | 只证明了**样式规则**会赢，没证明 hover 会被触发 |
| 2 | 加了 `elementFromPoint` 命中检查 | 能证明「没被挡住」，但当时压根没跑起来（headless 默认视口太小，元素在视口外，返回 null） |

真正的原因：**`.petart` 是 `position:relative` 且 DOM 顺序在灯泡之后，
两者都 `z-index:auto`，于是它盖在灯泡上面**，鼠标事件根本到不了灯泡——
hover 不触发，点击还会被 `.petbox` 接走去开合菜单。加 `z-index:3` 才解决。

**样式生效 ≠ 事件送达。** 定位元素之间只要没写 z-index，就是 DOM 顺序说了算。

验证用 `node tools/ui_probe.mjs <页面> <选择器> --setup "<摆状态的 DOM 操作>"`：
起一个带调试端口的 Chrome，派发真实的 `mouseMoved` / `mousePressed`，
报三项——命中测试、`:hover` 是否匹配、hover 前后的 transform。
去掉 `z-index` 重跑会立刻变红，可以当回归用。

⚠️ `--setup` 里只能用 DOM API：原型脚本包在 IIFE 里，`setHint()` 这些私有函数
从 `Runtime.evaluate` 够不着，得直接加删 class 来摆状态。

### 5.3.3 proto_smoke 看不见 null 引用，还要跑一次真实浏览器

`proto_smoke.mjs` 的 DOM 桩里 **`querySelector` 永远返回一个元素**。
真实浏览器里选择器打偏会返回 `null`，下一行 `.offsetHeight` 就抛 TypeError，
整个 IIFE 从那里断掉——桩完全看不到，还会报「✓ 顶层执行 + 初始渲染」。

实际踩过：把 `.pa.idle` 改名成 `.pa.mag` 后，`selfCheck()` 里还查着旧名字，
页面一加载就抛错、后面所有交互都没绑定。是用 CDP 抓 `Runtime.exceptionThrown`
才定位到的。

所以改完原型要跑两个：

```bash
node tools/proto_smoke.mjs prototypes/<页面>.html    # 快，逐视图渲染
node tools/page_console.mjs prototypes/<页面>.html   # 慢，真实运行时异常
```

**重命名 class 时尤其要跑第二个**——CSS 里改了、JS 里漏改，只有真实浏览器会喊。

### 5.4 视觉改动不生效时，先算盒模型，别猜素材

这个 bug 我连改三轮没解决，因为一直在猜**素材**的问题（图标画布内边距、归一化基准、
重心裁切），而真正吃掉宽度的是**元素默认样式**。三轮里改对了两个真 bug，
但都被这个更大的坑盖住，看不出任何效果。

**正确的排查顺序**：
1. 把两个"应该一样却不一样"的选择器**并排打印出来**，包括继承和 UA 默认值；
2. 手算内容区尺寸（`width − border×2 − padding×2`），确认百分比的基准是什么；
3. 确认基准没问题，再去查素材。

判断依据是"两处渲染结果不一致"，而不是"我觉得偏小"——
后者会让人一直在调数值，前者能直接把范围缩到两个选择器的差异上。

### 5.5 内边距不要烘进图片

早期图标画布自带 20% 内边距，CSS 写 `88%` 实际只占直径 70%。
留白应该完全由 CSS 控制，图片里只放图形本体，否则后面每个人调 CSS
都在跟一个看不见的系数较劲，而且这个系数每个图标还不一样。

### 5.6 圆形按钮里的图标按外接圆归一化

见第 4 节 UI 美术资源清单。按外接框归一化会让细长形状显小、方形显大；
按重心居中时画布必须由外接圆半径反推，否则会把图形裁掉一角。

### 5.7 CSS 3D：面朝向和法线都要实测，不能照直觉填

掷骰动画做过一版 CSS 立方体（`prototypes/archive/dice-roll-v2-cube.html`，**已否决**，
定稿用的是平面切面的 v1）。方案虽然没采用，两个坑对以后任何 3D 界面都成立，
都是「名字像什么」压过了「算出来是什么」：

- **面的贴图方向**：`rotateX(±90deg) translateZ()` 贴上去的面，整体转正后贴图是正立还是
  倒的、左右有没有镜像，光看代码判断不了。做法是先渲染一张对照图——六个立方体分别摆在
  「让第 N 面正对镜头」的角度，截图逐个核对点数和方向，确认后才写动画。
- **面的法线**：`.f5` 写的是 `rotateX(-90deg)`，它的局部法线是 `[0,1,0]` 而不是直觉上
  「顶面 = -Y」的 `[0,-1,0]`。填反的后果是这一面转到正面时被算成背光，整颗骰子发灰。
  法线必须把 `[0,0,1]` 过一遍该面自己的 transform 算出来。

排查这类问题不要靠肉眼看动画。本机有 headless 浏览器可直接截图：

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu \
  --hide-scrollbars --window-size=1180,1080 --screenshot=out.png "file://$PWD/prototypes/xxx.html"
```

动画本身也能这样验收：按同一套公式把 p=0…1 切成十几帧并排渲染成一张接触表，
高度、旋转、位移的分布一眼可见。第一版的旋转就是这样发现「p≈0.65 就转完了、
后面 35% 时间只在原地小跳」的——单看动画只觉得「有点拖」，说不出哪里拖。

### 5.8 面板尺寸要按 3D 的视觉外扩预留，不是按元素盒子

96px 的立方体转起来，对角线方向的视觉外扩到 150px 上下，比它的 `width/height` 大得多。
按盒子尺寸算净空，骰子弹到最高点时会直接糊到上方控件上——`.lift` 是 96×96，
但立方体的角早就伸到框外去了。3D 元素上方的留白要按半对角线算，再加上位移幅度。

## 6. AI 出图会反复踩的坑

### 6.1 读物品数据用 `catalog.bundled.json`，别解析 `catalog.*Loot.ts`

**`src/domain/catalog.bundled.json` 是唯一真实来源**，直接 `json.load` 即可，不需要正则。
那几个 `catalog.*Loot.ts` 已经没有任何地方引用，是死文件，数值可能和线上不一致。

历史教训（如果非要解析 ts）：物品定义的字段会增删（先后加过 `stackSize`、`sellable`、`tags`），
重量和售价也整体重配过（麻绳 3.0 → 0.3、毛皮 3.5 → 0.6、铸铁锅 12.5 → 4.0）。
按「`weight` 后面紧跟 `sellValue`」写的正则会在某次改表后**一件都匹配不上**，
而且不报错、只是静默返回空。要解析就先按 `id: "..."` 切块、再在块内按字段名逐个取值。



来自动画和图标两条管线的实战记录，完整版在 `loot/RARITY-PALETTE.md`。

- **道具消失得自不自然，取决于消失位置，不是速度。** 贴着身体绕到背后、被侧轮廓挡掉是对的；
  在胸前原地缩小或在空地上淡出是穿帮。这条判据同时管住了睡眠、成功、失败三组动画。
- **道具尺寸靠改持法控制，不靠形容词。** 反复写「约为她的头那么大」无效；
  改成「一只翅膀捏住袋口细绳、袋子悬空垂在身侧」后尺寸立刻收敛——物理上就抱不起来了。
- **手臂必须写死是企鹅翅膀**，否则模型会在拎东西时把翅膀变形成人类手掌。
- **已验收的提示词句子不要重写。** 改动构图、背景色这类"看起来无害"的句子会引发风格漂移。
  中灰背景方案就是这么被否掉的：做了浅灰 / 中灰对照实验，画面确实变了，收益却已被别的办法覆盖。
- **改动前先做对照实验，代价只有一张图。**
